01

RL ki bunyaad — agent, environment, reward

Machine learning ke teen bade khaane hain. Supervised learning me har input ka sahi jawab pehle se diya hota hai ("is photo me billi hai"). Unsupervised me jawab hota hi nahi, sirf data me pattern dhoondhna hota hai. Reinforcement learning teesra hai: sahi jawab koi nahi batata, lekin har koshish ke baad ek number milta hai — reward — jo kehta hai "ye chaal kitni achhi thi".

Yahi hamare project ke liye zaroori tha. Kisi ne kabhi nahi bataya ki "circle banane ke liye 240 steps me kaunse (dx, dy) sahi hain". Agar hum wo bata dete, to wo RL nahi, sirf ek pre-programmed trajectory hoti — aur project ki novelty hi khatam.

Return: sirf abhi ka reward kaafi nahi

Agar agent sirf agle step ka reward dekhe, to wo lalchi ho jayega. Drawing me aksar ek chaal abhi kuch nahi deti lekin aage ke 50 steps aasaan kar deti hai (jaise square ke corner par mudna). Isliye RL "abhi ka reward" nahi, return maximize karta hai — aaj se lekar episode ke ant tak ke saare rewards ka jod.

Discounted return
Gt = rt+1 + γ rt+2 + γ2 rt+3 + … = Σk=0∞ γk rt+k+1
  • GtTime t se aage ka kul inaam. RL ka asli maqsad yahi badhana hai — ek step ka reward nahi.
  • rt+1Agle step par mila reward. Hamare yahan: IoU kitna badha.
  • γDiscount factor, 0 se 1 ke beech. Ye kehta hai "door ka reward aaj ke reward se thoda kam keemti hai". Hamare project me gamma=0.99.
  • ΣJod — saare future steps ka.

γ ko aise samjhein: γ = 0 matlab agent bilkul lalchi, sirf agla step dekhta hai. γ = 0.99 matlab agent ko lagbhag 100 steps aage tak ki parwah hai (rough thumb rule: horizon ≈ 1/(1−γ) = 100). Hamare episode 240 steps ke hain, to 0.99 theek baithta hai — agent poore shape ke baare me soch sakta hai, lekin infinity tak nahi.

Policy, Value aur Q — teen cheezein jo RL seekhta hai

Ye teen naam poore RL me baar-baar aayenge, isliye ek baar theek se:

Policy — "kya karun?"
π(a | s) = state s me action a chunne ka probability
  • πAgent ka dimaag. Hamare project me ye ek CNN hai jo 64×64×3 image leta hai aur (dx, dy) ka mean aur standard deviation deta hai — yaani ek Gaussian distribution, jisme se action sample hota hai.
  • θPolicy ke andar ke neural network weights. πθ likhne ka matlab: "wo policy jo in weights se banti hai". Training = θ badalna.
State value — "ye jagah kitni achhi hai?"
Vπ(s) = Eπ[ Gt | st = s ]
  • V(s)"Agar main abhi is halat me hoon aur aage apni hi policy se khelun, to average me kitna kul reward milega?"
  • EExpectation = average. Isliye kyunki policy aur environment dono me randomness hai — ek hi state se har baar alag return mil sakta hai.
  • GtUpar wala return.
Action value — "yahan se ye chaal kitni achhi hai?"
Qπ(s, a) = Eπ[ Gt | st = s, at = a ]
  • Q(s,a)V se ek kadam zyada detail: "is state me ye khaas action lene ke baad kitna milega". Q-Learning, SARSA aur DQN — teeno isi Q ko seekhte hain.
  • rishtaV(s) = Σa π(a|s) · Q(s,a). Yaani V, Q ka policy ke hisaab se average hai.
Hamare project me

PPO dono seekhta hai — policy π (kya karna hai) aur value V(s) (ye halat kitni achhi hai). Q kabhi nahi seekhta. Ye chhoti si baat aage section 13 me bahut badi wajah banegi ki humne DQN kyu nahi liya.

02

Model-based vs Model-free RL

"Model" ka yahan matlab neural network nahi hai. Model ka matlab hai: environment ka niyam — agar main state s me action a karun, to aage kya hoga aur kitna reward milega? Formally do cheezein: transition P(s′|s,a) aur reward R(s,a).

Model-based

Agent ke paas duniya ka naksha hai

Agent apne dimaag me aage ki chaal simulate kar sakta hai bina asli duniya me kiye — jaise chess player mann hi mann 5 chaal aage sochta hai. Bahut kam data me seekhta hai, lekin agar naksha galat hua to agent confidently galat plan banata hai.

Model-free

Agent sirf koshish karke seekhta hai

Koi naksha nahi. Action karo, jo hua so hua, reward dekho, policy thodi si badlo. Zyada data chahiye, lekin kabhi galat naksha ka shikaar nahi hota. PPO, SAC, DQN, Q-Learning — sab model-free.

Hamare project me — ek dilchasp mod

Hamare paas poora model maujood hai: PyBullet simulator exactly janta hai ki pen kahan jayega aur kaunsa pixel kaala hoga. Phir bhi humne model-free PPO chuna. Kyu?

Kyunki asli maqsad hardware par jaana hai (sim-to-real). Asli robot ke paas na PyBullet hai, na ye pata hai ki asli pen ki ink kaise failegi, na camera ka noise. Agar agent simulator ke exact model par nirbhar ho jaye, wo simulator ka expert banega, robot ka nahi. Model-free agent sirf "action → jo dikha → reward" seekhta hai — aur ye teeno cheezein asli robot par bhi maujood hain.

Yahi wajah reward_mode="vision" ke peeche bhi hai: hum jaan-boojh kar agent ko camera ki noisy nazar se reward dete hain, ground truth se nahi — kyunki asli duniya me ground truth hota hi nahi.

03

Exploration vs Exploitation, aur greedy selection

Ye RL ka sabse purana dwand hai. Aapko ek nayi jagah me 30 din khana khana hai. Pehle din jo restaurant achha laga — kya baaki 29 din wahi jaayein (exploitation: jo pata hai usme se best chuno), ya naye restaurant try karein is umeed me ki koi behtar mile (exploration)? Sirf exploit karoge to shayad shehar ka sabse achha khana kabhi na milega. Sirf explore karoge to har din average khana khaoge.

Greedy selection

Pure greedy policy
a = arg maxa Q(s, a)
  • arg maxa"Wo action jiska Q sabse zyada hai." max value deta hai, arg max wo action deta hai jisne wo value di.
  • Q(s,a)Agent ka abhi ka andaaza ki ye action kitna achha hai — jo aksar galat hota hai, khaaskar shuruaat me.

Pure greedy ka khatra: shuruaat me sab Q galat hote hain. Agar pehli baar galti se ek bekaar action ka Q thoda zyada aa gaya, agent hamesha wahi chunega, doosre action kabhi try hi nahi karega, aur unka Q kabhi sudhrega nahi. Agent ek local optimum me phans jata hai.

ε-greedy — sabse simple ilaaj
a = { arg maxa Q(s,a)  probability 1 − ε se  ;  koi bhi random action  probability ε se }
  • εChhota number, jaise 0.1. Yaani 10% baar agent jaan-boojh kar "bewakoofi" karta hai taaki nayi cheez pata chale.
  • decayAam tareeka: ε ko 1.0 se shuru karke dheere-dheere 0.05 tak girana — shuru me sab try karo, baad me jo seekha usko istemal karo.

Continuous actions me exploration kaise hota hai

ε-greedy tab kaam karta hai jab actions ginti ke hon (upar/neeche/left/right). Hamara action (dx, dy) hai — do real numbers, infinite possibilities. Inme "random action" ka matlab alag hai.

PPO ki policy ek action nahi deti, wo ek Gaussian distribution deti hai: mean μ(s) aur standard deviation σ. Action us distribution se sample hota hai. Agar σ bada hai, agent alag-alag cheezein try karta hai (exploration). Agar σ chhota hai, wo har baar lagbhag apni sabse achhi chaal chalta hai (exploitation). Aur σ khud seekha jata hai — koi ε schedule hand se set karne ki zaroorat nahi.

Entropy bonus — exploration ko zinda rakhne ka tareeka
Ltotal = Lpolicy − cv Lvalue + ce · H[πθ(·|s)]
  • H[π]Entropy = policy kitni "undecided" hai. Bada σ → bada H. Ise loss me plus karke hum agent ko inaam dete hain ki wo jaldi ek hi chaal par fix na ho jaye.
  • ceEntropy coefficient. Hamare project me ent_coef=0.02 — SB3 ka default 0.0 hai, humne jaan-boojh kar badhaya.
Hamare project me — ek asli local optimum jo humne dekha

Shuru me hamara reward sirf "target ke kitne pixel dhak gaye" tha. Agent ne kya seekha? Kuch bhi mat banao. Kyunki pen ko idhar-udhar ghumane se stray ink banti thi, IoU girta tha, reward negative aata tha — aur kuch na karne se reward 0 rehta tha. 0 > negative, to "kuch na karo" hi best policy ban gayi. Ye classic exploration failure hai: achhi drawing tak pahunchne ka raasta shuru me bura lagta hai.

Do cheezon ne ise toda: ent_coef=0.02 (agent ko zabardasti alag cheezein try karwaayi) aur potential-based shaping (section 15) — jo pen ko target ke paas aane par hi reward de deta hai, ink banane se pehle.

04

Monte Carlo methods — poora episode khelo, phir seekho

Ab sawaal ye hai: V(s) ya Q(s,a) hum seekhte kaise hain? Sabse seedha jawab: kai baar khelo aur average nikaalo. Yahi Monte Carlo (MC) hai.

Naam "Monte Carlo" casino se aaya hai — matlab "random samples se andaaza lagana". Agar aapko puchha jaye "is dice game me average kitne point milte hain?", to aap ya to poora probability ka ganit karein, ya bas game 10,000 baar khel kar average nikaal lein. Doosra tareeka Monte Carlo hai.

Poora episode kheloShuru se ant tak. Hamare project me: 240 steps, poori drawing ban jaane tak.
Ab peeche ki taraf return ginnoHar state ke liye Gt nikaalo — us state ke baad jo bhi reward mila uska discounted jod.
Andaaza average ki taraf khiskoV(s) ko dekhe hue G ki taraf thoda sarkao.
Monte Carlo value update
V(st) ← V(st) + α [ Gt − V(st) ]
  • V(st)Ab tak ka andaaza ki ye state kitni achhi hai.
  • GtAsli, poora, dekha hua return — koi andaaza nahi, koi guess nahi. Episode khatam hone ke baad ye exactly pata hota hai.
  • αLearning rate, jaise 0.01. "Nayi jaankaari ki taraf kitna khisko."
  • [ … ]Error: "jo asli me mila" minus "jo maine socha tha". Agar positive, to state ko maine kam aanka tha — V badhao.
monte_carlo.pyconcept demo — project code nahi
# Ek episode khelo, poora. Kuch mat seekho beech me.
episode = []
s, _ = env.reset()
done = False
while not done:
    a = policy(s)
    s2, r, term, trunc, _ = env.step(a)
    episode.append((s, a, r))      # sirf jama karo
    s, done = s2, term or trunc

# Episode KHATAM. Ab peeche se aage badho aur return ginno.
G = 0.0
for s, a, r in reversed(episode):
    G = r + gamma * G              # G_t = r_{t+1} + gamma * G_{t+1}
    V[s] = V[s] + alpha * (G - V[s])   # asli return ki taraf khisko

reversed() zaroori hai: Gt ko ginne ke liye Gt+1 chahiye, isliye ant se shuru karo. Ye choti si trick MC ka poora kaam hai.

MC ki sabse badi khoobi

MC me koi bias nahi hai. Gt asli dekha hua return hai, kisi doosre andaaze par nirbhar nahi. Isliye agar aap kaafi episodes chala lein, MC ka jawab bilkul sahi value par pahunchta hai — guarantee ke saath. Isi wajah se ye samajhne ke liye sabse aasan method hai.

05

Monte Carlo ke problems

MC saaf hai, lekin practical robotics me ye kai jagah toot jata hai. Ye chaar dikkatein seedhe RoboSketch-RL par lagti hain — aur yahi wajah hai ki hamara project MC use nahi karta.

Problem 1 — Episode khatam hone ka intezaar

MC kuch seekh hi nahi sakta jab tak episode poora na ho. Hamare env me ek episode 240 steps ka hai. Agar agent ne step 3 par ek shandar chaal chali, use uska credit step 240 tak nahi milta. Sochiye ek student jise poore saal padhne ke baad sirf ek final marksheet mile — wo kaise jaane ki kaunsa chapter theek tha?

Aur jo task kabhi khatam hi nahi hota (continuing tasks — jaise ek robot jo lagataar chalta rahe), wahan MC lag hi nahi sakta. Uska Gt kabhi calculate hi nahi hoga.

Problem 2 — Bahut zyada variance

Ye sabse gambhir hai. Gt me 240 steps ki saari randomness jama ho jati hai. Ek hi state se do baar chal kar dekhiye — policy ne alag actions sample kiye, alag jagah pen gaya, alag drawing bani, aur Gt bilkul alag aaya. Aapka signal shor me doob jata hai.

Problem 3 — Har step ka data barbaad hota hai

MC ek poore episode (240 transitions) se sirf ek "learning event" banata hai. TD wahi 240 transitions se 240 updates nikaal leta hai. Robotics me jahan har step mehnga hai (asli robot, asli time), ye barbaadi bardaasht nahi hoti.

Problem 4 — Bootstrapping nahi, isliye online nahi

MC "bootstrap" nahi karta — yaani wo apne hi purane andaaze ka istemal nahi karta. Sunne me imaandari lagti hai, lekin iska nateeja ye hai ki MC online nahi seekh sakta, aur wo apni pehle seekhi hui cheezon ka fayda nahi utha sakta.

Isliye koi bhi modern deep RL algorithm — DQN, PPO, SAC — pure Monte Carlo nahi hai. Sabhi TD ya TD-jaisi cheez istemal karte hain. PPO ka GAE (section 11) exactly wahi hai: MC aur TD ke beech ka ek dial.

06

TD methods — har step par thoda-thoda seekho

Temporal Difference (TD) learning RL ka sabse khoobsurat idea hai. Poora return dekhne ka intezaar mat karo. Ek step chalo, ek reward dekho, aur baaki ke liye apne hi andaaze par bharosa karo.

Ise bootstrapping kehte hain — apne joote ke feete kheench kar khud ko uthana. Sunne me chakkar wala lagta hai (galat andaaze se galat andaaza sudhaarna?), lekin ganitiya taur par ye kaam karta hai, kyunki har update me ek asli reward r ghusta hai. Wo asli reward dheere-dheere poore system ko sach ki taraf kheenchta hai.

TD(0) — sabse buniyaadi TD update
V(st) ← V(st) + α [ rt+1 + γ V(st+1) − V(st) ]
  • rt+1Ek asli reward, abhi mila hua. Ye sach ka tukda hai.
  • γV(st+1)Bootstrap term. "Aage ka poora return main nahi jaanta, lekin agli state ka mera andaaza ye hai." MC yahan poora Gt rakhta tha; TD sirf andaaza rakhta hai.
  • V(st)Purana andaaza, jise sudhaarna hai.
  • αLearning rate.

Bracket ke andar wali cheez itni important hai ki uska apna naam hai:

TD error — poore RL ka sabse zaroori number
δt = rt+1 + γ V(st+1) − V(st)
  • δt"Surprise". Jitna maine socha tha usse kitna behtar/bura nikla. δ > 0 = umeed se achha hua. δ = 0 = bilkul waisa hi jaisa socha tha, kuch seekhne ko nahi.
  • majedaarDimaag me dopamine neurons lagbhag isi δ jaisa signal firing karte hain — RL ka ye hissa neuroscience se milta hai.

δ aage har jagah dikhega: SARSA me, Q-Learning me, DQN me, aur PPO ke GAE me — GAE to seedhe-seedhe δ ka ek weighted jod hai.

Beech ka raasta — n-step aur λ

MC aur TD do sire hain ek hi line ke. TD(0) 1 step dekhta hai, MC saare steps. Beech me n-step TD hai: n steps ke asli reward lo, phir bootstrap karo. n jitna bada, MC ke utna kareeb (kam bias, zyada variance).

Aur agar aap saare n ka ek weighted average le lein, to TD(λ) milta hai — jismein λ ek knob hai 0 (pure TD) se 1 (pure MC) tak. PPO ka GAE-λ bilkul yahi cheez hai, advantage ke liye. Isliye ye section PPO samajhne ke liye zaroori tha.

07

On-policy vs Off-policy — ek hi sawaal, do jawab

Har RL algorithm ke paas do policies hoti hain, chahe wo alag hon ya ek hi:

Behaviour policy

Jo data banati hai

Wo policy jo asal me environment me actions le rahi hai — jiske transitions collect ho rahe hain.

Target policy

Jo seekhi ja rahi hai

Wo policy jise hum behtar bana rahe hain, jise ant me use karenge.

On-policy: dono ek hi hain. Agent apni hi chaal se seekhta hai. Data policy ke saath purana ho jata hai — jaise hi policy badli, purana data invalid.

Off-policy: dono alag ho sakti hain. Agent kisi aur ke (ya apne purane) data se seekh sakta hai. Isliye purana data replay buffer me sambhal kar rakha ja sakta hai aur baar-baar istemal ho sakta hai.

Ek aasan misaal

On-policy = aap khud gaadi chala kar driving seekh rahe hain. Jo aap karte ho, ussi se seekhte ho. Imaandaar, lekin dheema — aur aapko apni hi galtiyon se guzarna padta hai.

Off-policy = aap YouTube par doosron ki driving dekh kar seekh rahe hain, aur apni 3 saal purani recordings bhi dubara dekh rahe hain. Bahut zyada data se fayda, lekin ek pech hai: wo videos aapki abhi wali driving style ke nahi hain, to unse seekha hua sabak thoda galat ho sakta hai. Isi pech ko theek karne ke liye off-policy algorithms me importance sampling ya Q-learning ka max operator lagta hai.

08

SARSA aur Q-Learning — ek chhote se farak ki badi kahani

Ye do algorithms lagbhag ek jaise dikhte hain. Unke beech ka farak sirf ek term ka hai. Lekin wahi ek term on-policy aur off-policy ka poora farak hai — aur unka behaviour bilkul alag kar deta hai.

SARSA — on-policy

Naam khud algorithm hai: State, Action, Reward, agla State, agla Action. Update ke liye paanchon cheezein chahiye — aur "agla action" wo hai jo agent ne asal me liya.

SARSA update
Q(st, at) ← Q(st, at) + α [ rt+1 + γ Q(st+1, at+1) − Q(st, at) ]
  • Q(s′, a′)Yahi asli baat hai. a′ wo action hai jo policy ne asal me chuna — agar policy ε-greedy hai to a′ kabhi-kabhi random bhi hoga. Yaani SARSA apni hi galtiyon ko hisaab me leta hai.
  • rt+1Asli mila reward.
  • natijaSARSA "meri abhi wali (thodi random) policy kitni achhi hai" seekhta hai — isliye on-policy.

Q-Learning — off-policy

Ek hi shabd badalta hai: asli liye gaye action ki jagah, sabse achhe action ki value.

Q-Learning update
Q(st, at) ← Q(st, at) + α [ rt+1 + γ maxa′ Q(st+1, a′) − Q(st, at) ]
  • maxa′"Agli state me jo sabse achha action ho sakta tha, uski value." Isse fark nahi padta ki agent ne asal me kya kiya. Isliye off-policy — behaviour policy explore kar rahi hai, lekin seekhi ja rahi hai perfect greedy policy.
  • faydaAgent bewakoofi bhari exploration karte hue bhi optimal policy seekh sakta hai. Yahi DQN ki buniyaad hai.
  • nuksaanmax hamesha upar wale andaaze uthata hai, isliye Q-values ka over-estimation ho jata hai — Double DQN isi ko theek karta hai.
sarsa_vs_qlearning.pyfarak sirf ek line ka hai
# --- SARSA (on-policy) ---------------------------------
a  = eps_greedy(Q, s)
while not done:
    s2, r, done, _ = env.step(a)
    a2 = eps_greedy(Q, s2)                 # ASLI agla action (random ho sakta hai)
    target = r + gamma * Q[s2][a2]         # <-- wahi action jo liya jayega
    Q[s][a] += alpha * (target - Q[s][a])
    s, a = s2, a2

# --- Q-Learning (off-policy) ---------------------------
while not done:
    a = eps_greedy(Q, s)
    s2, r, done, _ = env.step(a)
    target = r + gamma * max(Q[s2])        # <-- BEST action, chahe wo liya jaye ya nahi
    Q[s][a] += alpha * (target - Q[s][a])
    s = s2

Ye farak dikhta kaisa hai — Cliff Walking

RL ka sabse mashhoor demo. Ek grid hai, neeche ki kataar me khai (cliff) hai. Khai me gire to bada minus reward aur episode khatam. Start bottom-left, goal bottom-right. Dono agents ε-greedy se explore karte hain (10% chaalein random).

Hamare project se rishta

SARSA aur Q-Learning dono tabular hain — ek table jisme har (state, action) ke liye ek khaana ho. Hamare state 64×64×3 ki image hai, aur action do real numbers. DQN — Q-table ki jagah neural network

Table kaam kyu nahi karta

Ek chhota hisaab jo sab kuch saaf kar deta hai. Hamari observation hai 64 × 64 × 3 uint8 image. Iska matlab 12,288 pixels, har ek 256 values me se koi bhi. Kul possible states:

Hamare state space ka aakar
|S| = 25664×64×3 = 25612288 ≈ 1029,592
  • tulnaPoore brahmand me lagbhag 1080 atoms hain. Hamara state space uska 1029,512 guna hai. Table banane ka koi sawaal hi nahi.
  • halFunction approximation — har state ko yaad rakhne ki jagah, ek neural network se andaaza lagao. CNN ko ye bhi samajh aa jata hai ki "milti-julti tasveeron ki value milti-julti hoti hai" — jo table kabhi nahi seekh sakta.

DQN ka core

DQN (Deep Q-Network, 2015) ne Q-Learning ka wahi update liya aur Q-table ki jagah CNN rakh diya. Table update ki jagah ab ek loss minimize hota hai:

DQN loss
L(θ) = E[ ( r + γ maxa′ Q(s′, a′; θ−) − Q(s, a; θ) )2 ]
  • θMain network ke weights — jo abhi train ho rahe hain.
  • θ−Target network — wahi network, lekin kuch hazaar steps purani copy, jise jam kar rakha jata hai. Iske bina target har step badalta rehta hai aur training phat jati hai ("apni hi poonch ka peechha").
  • maxa′Q-Learning wala max. Yeh saare possible actions par lagta hai — is line par section 13 ka poora faisla tika hai.
  • rReplay buffer se nikaala gaya ek purana transition ka reward.
Trick 1

Experience replay

Lakhon purane transitions ek buffer me rakho aur unme se random mini-batch nikaal kar train karo. Isse lagataar aane wale data ka correlation tootta hai, aur har transition kai baar kaam aata hai. Ye sirf isliye legal hai kyunki Q-Learning off-policy hai.

Trick 2

Target network

Target ke liye ek jami hui purani copy. Ye "chal-goal" problem hataata hai. Dono tricks ke bina DQN Atari par kaam hi nahi karta tha.

DQN ki wo ek limitation jo hamare liye faisla-kun hai

DQN sirf discrete actions par chalta hai

Har jagah maxa′ Q(s′, a′) likha hai. Ise nikaalne ke liye aapko har action ka Q ginna padta hai aur sabse bada chunna padta hai. Atari me ye aasan hai — 18 buttons, 18 numbers, max le lo.

Hamara action (dx, dy) ∈ [−1, 1]2 hai — infinite actions. "Sabse achhe action" ko dhoondhne ke liye har step par ek poora optimization problem hal karna padega. Har step par. 200,000 steps ke liye. Ye vyavhaarik hai hi nahi.

Iska jugaad hai — action ko discretize karna, jaise 8 dishaayein. Lekin phir aap kabhi 22.5° ka smooth arc nahi bana sakte, aur circle banana hi hamara task hai. Isliye DQN yahin bahar ho jata hai.

Policy Gradient aur Actor-Critic

Ab tak har algorithm ne value seekhi (Q ya V) aur policy usse nikaali — "sabse zyada Q wala action chuno". Policy gradient ek doosra hi raasta pakadta hai: policy ko seedhe seekho. Network hi batayega kya karna hai; Q ko beech me laane ki zaroorat nahi.

Ye do wajah se badiya hai. Pehla, continuous actions apne aap chalte hain — network Gaussian ka mean de dega, koi max lena hi nahi hai. Doosra, policy stochastic ho sakti hai, jo exploration aur partial observability dono me madad karta hai.

Policy gradient theorem — REINFORCE
∇θ J(θ) = E[ ∇θ log πθ(at|st) · Gt ]
  • ∇J(θ)Wo dishaa jisme weights badalne se kul reward badhega. Gradient ascent isi par chalta hai.
  • ∇ log π"Is action ki probability badhane ki dishaa." Akela ye kehta hai: jo kiya, uska chance badha do.
  • GtReturn — kitna badhana hai. Achha nikla to zyada, bura nikla to negative (yaani ghata do).
  • saar"Jo chaal achhi nikli, use aage zyada karo. Jo buri nikli, kam karo." Bas itna hi hai.

Lekin dhyaan dein — ismein Gt hai, yaani Monte Carlo return. Section 05 wali saari problems yahan wapas aa gayi: bahut zyada variance, episode ke ant ka intezaar. REINFORCE isi wajah se practically dheema aur ustable hai.

Do sudhaar jo PPO tak le jaate hain

Sudhaar 1 — Baseline aur Advantage

Maan lijiye har action ka return +100 se +110 ke beech hai. Gt hamesha bada positive hai, to gradient har action ki probability badhata hai — achhe aur bure dono ki. Sirf thoda alag-alag. Ye behad shor bhara signal hai.

Ilaaj: return me se ek baseline ghata do — V(s), yaani "is state me average kitna milta hai". Jo bacha wo hai advantage.

Advantage
A(s, a) = Q(s, a) − V(s)
  • A(s,a)"Ye action is state ke average se kitna behtar tha." Positive = average se achha, probability badhao. Negative = average se bura, ghatao.
  • V(s)Baseline. Isse gradient ka bias nahi badalta, sirf variance girta hai — ye ek ganitiya guarantee hai.
  • faaydaAb "sab kuch +100 hai" wali situation me bhi signal saaf hai: 105 wala action average se achha, 102 wala bura.

Sudhaar 2 — Actor-Critic

Advantage ke liye V(s) chahiye. To ek doosra network usko seekh lega. Ab do hisse hain:

Actor

Policy πθ(a|s)

Kaam karta hai — action chunta hai. Advantage ke hisaab se update hota hai.

Critic

Value Vφ(s)

Judge karta hai — batata hai ye state kitni achhi thi. TD se train hota hai (section 06 wala δ).

GAE — advantage ka MC-to-TD dial

Advantage ka andaaza kaise lagayein? Do sire hain, wahi jo section 06 me the:

Generalized Advantage Estimation (GAE-λ)
At = δt + (γλ)δt+1 + (γλ)2δt+2 + …   jahan  δt = rt + γV(st+1) − V(st)
  • δtWahi TD error jo section 06 me mila tha. GAE unka ek weighted jod hai — isliye TD samajhna zaroori tha.
  • λDial. λ = 0 → sirf δt, yaani pure TD: kam variance, thoda bias. λ = 1 → Monte Carlo: bias zero, variance chhat par. Practical default λ = 0.95 — jo hamare project me bhi chal raha hai (SB3 ka gae_lambda).
  • yaaniPPO na pure MC hai, na pure TD — wo dono ke beech ek tuned mixture hai. Section 04 se 06 tak ka saara safar yahan aakar jud jata hai.
Ab bhi ek badi problem baaki hai

Actor-critic ke baad bhi policy gradient me ek jaanleva dikkat hai: step size. Kitna bada gradient step lein? Chhota lein to training kachhue ki chaal chalti hai. Bada lein to policy ek hi update me tabaah ho sakti hai — aur supervised learning ke ulat, yahan wapasi nahi hoti, kyunki agli baar ka data usi tooti hui policy se aayega. Yahi wo problem hai jise PPO hal karta hai.

PPO — Proximal Policy Optimization

"Proximal" ka matlab hai paas ka. PPO ka poora idea ek line me: policy ko sudharo, lekin ek update me itna mat badlo ki wo pehchan me hi na aaye.

11.1 — Wo problem jise PPO hal karta hai

Policy gradient kehta hai "is dishaa me chalo". Wo ye nahi batata ki kitna chalo. Aur RL me galat step size sirf dheemi training nahi, poori tabaahi laata hai:

Ek bada gradient step lagta haiPolicy achanak bahut badal jati hai.
Nayi policy kharaab haiAb agent bekaar actions le raha hai.
Ab jo data aayega wo bhi bekaar hogaKyunki data isi tooti policy se aata hai. Supervised learning me dataset fix hota hai — RL me dataset khud policy banati hai.
Wapasi ka raasta nahiBekaar data se bekaar gradient, aur agent kabhi ubhar nahi paata. Ise performance collapse kehte hain.

TRPO (2015) ne iska sakht hal diya: policy ko itna badlo ki purani aur nayi policy ke beech KL-divergence ek limit se kam rahe. Ye kaam karta hai, lekin ismein second-order optimization aur conjugate gradient chahiye — likhna aur samajhna dono mushkil.

PPO (2017) ne wahi cheez ek behad saral trick se hasil ki, sirf clipping se. Aaj PPO robotics aur RLHF dono ka default hai kyunki wo TRPO jaisa stable hai aur likhne me 30 line ka.

11.2 — Probability ratio

Ratio — policy kitni badal gayi
rt(θ) = πθ(at|st) / πθold(at|st)
  • πθAbhi wali (naye weights se banti) policy is action ko kitna probability deti hai.
  • πθoldWo policy jisne ye data asal me banaya tha. Ye ek fix number hai, rollout ke waqt store kar liya jata hai.
  • rtr = 1 → policy bilkul nahi badli. r = 1.5 → nayi policy is action ko 50% zyada karti hai. r = 0.5 → aadha kar diya. Yaani r ek "kitna door chale gaye" ka meter hai.
  • code meProbability ka bhaag numerically kharaab hota hai, isliye hamesha log me kaam karte hain: ratio = exp(logp_new − logp_old).

11.3 — Clipped objective: PPO ka dil

PPO-Clip objective
LCLIP(θ) = Et[ min( rt(θ) At ,   clip(rt(θ), 1−ε, 1+ε) At ) ]
  • rtAtPehla term: aam policy gradient. Achha action (A > 0) → r badhao. Bura action (A < 0) → r ghatao. Akela ye term bina rok-tok chalega.
  • clip(r, 1−ε, 1+ε)Doosra term: wahi cheez, lekin r ko zabardasti [0.8, 1.2] ke andar daba kar (ε = 0.2). Yaani "policy 20% se zyada mat badalna".
  • min(·, ·)Yahi asli chaturai hai. Dono me se chhota lo. Iska matlab: PPO ka objective hamesha ek pessimistic lower bound hai. Zyada badalne ka koi faayda nahi milega, lekin zyada badalne se hone wala nuksaan poora dikhega.
  • AtGAE se nikala advantage (section 10). Iska sign hi tay karta hai ki clip kis taraf kaam karega.
  • εClip range, aam taur par 0.1–0.3. SB3 ka default clip_range=0.2 — hamare project me yahi chal raha hai.

Ye min kyu itna zaroori hai, ise ek tasveer se dekhna sabse aasan hai. Do haalat hain, is baat par depend karke ki action achha tha ya bura:

Ek line me clip ka matlab

"Ek update me policy ko 20% se zyada badalne ka koi inaam nahi milega — lekin agar wo galat taraf 20% se zyada chali gayi, to poori saza milegi." Isi tarah PPO bina KL constraint ke, bina second-order maths ke, TRPO ka kaam kar leta hai.

11.4 — Poora loss (teen hisse)

PPO ka final objective
Ltotal = LCLIP − c1 · (Vφ(st) − Vttarg)2 + c2 · H[πθ]
  • LCLIPActor. Upar wala clipped objective — achhe actions zyada, bure kam.
  • value lossCritic. Vφ ko sach ke kareeb laao. Vtarg = advantage + purani value. Coefficient c1 = 0.5 (SB3 default). Ghata isliye kyunki ye error hai, jise kam karna hai.
  • entropy HExplorer. Policy ko jaldi ek chaal par jamne se rokta hai. Hamare project me c2 = ent_coef=0.02.
  • code mePyTorch minimize karta hai, isliye code me sabhi sign ulat jate hain: loss = -policy_obj + c1*value_loss - c2*entropy.

Hissa 1 — Network: ek body, do heads

ppo_from_scratch.py1/4 — actor-critic network
import torch
import torch.nn as nn
from torch.distributions import Normal

class ActorCritic(nn.Module):
    """Ek hi CNN body, do heads:
       actor  -> action ka Gaussian (mean + std)
       critic -> V(s), ye state kitni achhi hai
    Body share karne se features dono ke liye ek baar seekhe jate hain."""

    def __init__(self, obs_ch=3, n_act=2):
        super().__init__()
        self.body = nn.Sequential(                    # 64x64x3 image -> 512 features
            nn.Conv2d(obs_ch, 32, 8, stride=4), nn.ReLU(),
            nn.Conv2d(32, 64, 4, stride=2), nn.ReLU(),
            nn.Conv2d(64, 64, 3, stride=1), nn.ReLU(),
            nn.Flatten(), nn.Linear(64 * 4 * 4, 512), nn.ReLU())
        self.mu      = nn.Linear(512, n_act)          # Gaussian ka MEAN, state se
        self.log_std = nn.Parameter(torch.zeros(n_act))  # SPREAD: state-independent,
                                                      # lekin seekha jata hai
        self.v       = nn.Linear(512, 1)              # critic head

    def dist_and_value(self, obs):
        h = self.body(obs / 255.0)                    # uint8 -> [0,1]
        dist = Normal(self.mu(h), self.log_std.exp()) # yahi hamari policy pi(a|s)
        return dist, self.v(h).squeeze(-1)

log_std ko parameter banane ka matlab: exploration ka size khud training me tay hota hai. Shuru me std bada hota hai (agent kaafi random hilta hai), aur jaise-jaise wo confident hota hai, std apne aap girta hai. ε-greedy ka schedule hand se likhne ki zaroorat khatam.

Hissa 2 — GAE se advantage

ppo_from_scratch.py2/4 — GAE-lambda
def compute_gae(rews, vals, dones, last_val, gamma=0.99, lam=0.95):
    """Advantage = "ye action average se kitna behtar tha".
    Peeche se aage chalte hain, kyunki A_t ko A_{t+1} chahiye."""
    adv, running = torch.zeros_like(rews), 0.0
    for t in reversed(range(len(rews))):
        next_val = last_val if t == len(rews) - 1 else vals[t + 1]
        mask     = 1.0 - dones[t]          # episode khatam ho gaya -> aage kuch nahi
        delta    = rews[t] + gamma * next_val * mask - vals[t]   # TD error (sec 06)
        running  = delta + gamma * lam * mask * running          # delta ka weighted jod
        adv[t]   = running
    returns = adv + vals                   # critic ka target
    return adv, returns

mask wali line chhoti dikhti hai lekin zaroori hai: episode khatam hone par agli state ki value ko zero karna padta hai, warna do alag episodes ka reward aapas me mil jayega. Hamare env me ye baat aur nazuk hai — hum terminated (agent ne shape bana liya / stop kaha) aur truncated (240 steps khatam) alag rakhte hain, kyunki truncation par value ko bootstrap karna chahiye, terminate par nahi.

Hissa 3 — PPO update (ye poora algorithm hai)

ppo_from_scratch.py3/4 — clipped update
def ppo_update(net, opt, obs, act, old_logp, adv, ret,
               clip=0.2, epochs=6, batch=256, c_v=0.5, c_e=0.02):

    # advantage normalise: mean 0, std 1. Isse learning rate har task par
    # ek jaisa kaam karta hai aur badi advantages update ko uda nahi deti.
    adv = (adv - adv.mean()) / (adv.std() + 1e-8)
    n = len(obs)

    for _ in range(epochs):                     # WAHI data, 6 baar
        for idx in torch.randperm(n).split(batch):
            dist, value = net.dist_and_value(obs[idx])
            logp  = dist.log_prob(act[idx]).sum(-1)   # dx aur dy dono ka jod
            ratio = (logp - old_logp[idx]).exp()      # r(theta), log me safe

            # ---- PPO ka dil: do terms, chhota wala lo ----
            unclipped = ratio * adv[idx]
            clipped   = ratio.clamp(1 - clip, 1 + clip) * adv[idx]
            policy_loss = -torch.min(unclipped, clipped).mean()
            # minus isliye: hum objective ko BADHANA chahte hain,
            # lekin optimizer loss ko GHATATA hai.

            value_loss = ((ret[idx] - value) ** 2).mean()   # critic
            entropy    = dist.entropy().sum(-1).mean()      # explorer

            loss = policy_loss + c_v * value_loss - c_e * entropy

            opt.zero_grad()
            loss.backward()
            nn.utils.clip_grad_norm_(net.parameters(), 0.5)  # ek aur safety belt
            opt.step()

13.3 — Wajah 1: action continuous hai (ye akela hi faisla kar deta hai)

Hamara agent kehta hai "pen ko 0.37 units daayen aur 0.12 units upar sarkao". DQN ki puri machinery maxa Q(s,a) par khadi hai — aur infinite actions par max lena sambhav nahi.

Iska ek jugaad hai: action ko discretize kar do, jaise 8 dishaayein × 3 lambaai = 24 actions. Lekin phir:

  • Circle sirf 8 dishaon se banega — wo circle nahi, octagon hoga. Aur circle hamare chaar targets me se ek hai.
  • Sim-to-real par ye aur bura hai: asli arm ke servo continuous angles lete hain; ek discretized policy jhatke se chalegi.
  • path_ratio (hamari efficiency metric) barbaad ho jayega, kyunki zig-zag majboori ban jayega.

PPO me ye samasya hai hi nahi. Network Gaussian ka mean deta hai, action sample hota hai, khatam. Koi max nahi, koi discretization nahi.

13.4 — Wajah 2: hamare project me off-policy kyu nahi

Off-policy ka bada faayda hai replay buffer — purana data baar-baar use karo. Lekin hamare khaas project me wo faayda kaafi had tak kaam ka nahi rehta, aur uske saath teen asli dikkatein aati hain.

Dikkat 1 — hamara reward khud badalta raha

Research ke dauraan hum reward function baar-baar badalte rahe: pehle coverage-only, phir ΔIoU, phir potential-based shaping, phir truth / vision / vision_real teen modes. Replay buffer me pada har purana transition us waqt ke reward function se ginaa gaya tha. Off-policy agent unhi purane, ab galat, rewards par train hota rehta.

On-policy me ye samasya hai hi nahi — har rollout abhi ke env aur abhi ke reward se aata hai, aur update ke baad phenk diya jata hai.

Dikkat 2 — hamara state canvas ke itihaas par tika hai

Hamare env me state ka ek channel hai "ab tak kya draw ho chuka". Wo canvas poore episode me jama hota hai. Aur reward ΔIoU hai — yaani usi canvas ka badlaav.

Iska matlab: ek transition (s, a, r, s′) apne poore itihaas se juda hua hai. Buffer me alag-alag episodes ke, alag-alag policies ke, alag-alag adhoore canvas ke transitions mila kar batch banana — ye kaam karta hai (DQN yahi karta hai) lekin ismein correlation aur non-stationarity dono bahut zyada hain. On-policy rollout me poore trajectories saath rehte hain, jo GAE ke liye zaroori bhi hai.

Dikkat 3 — research ke liye stability > speed

Hamara headline result H2 hai: "camera-reward agent ground-truth agent jitna hi achha hai". Ye claim tabhi tikta hai jab dono arms ek hi protocol par, kai seeds par, dobara chalane par wahi number dein.

Off-policy methods (khaaskar DDPG/TD3) seeds ke beech bahut bikharte hain. Agar hamara variance itna zyada hota, to 0.028 ka farak (H2 ka poora sawaal) shor me doob jata — aur paper me kuch kehne layak nahi bachta. PPO ka predictable behaviour yahan ek scientific zaroorat hai, sirf convenience nahi.

Aur off-policy ka faayda hamare liye chhota kyu hai

Off-policy ka asli inaam sample efficiency hai — jab har environment step mehnga ho (asli robot, asli waqt, asli tootne ka khatra). Hamara default sim use_arm=False hai: pen seedhe move hota hai, ink OpenCV se lagti hai, koi physics nahi. Ye itna sasta hai ki 8 environments parallel me chalte hain aur 200,000 steps minton me poore hote hain.

Yaani hum wo cheez kharid rahe hain (stability) jo hamare paas kam hai, us cheez ke badle (sample efficiency) jo hamare paas kaafi hai. Yahi sahi sauda hai.

Imaandaar baat — ye faisla hamesha ke liye nahi hai

Jab hum sim-to-real par jaayenge, samikaran badal jayega: asli robot par har step mehnga hoga, reward function tab tak fix ho chuka hoga, aur sample efficiency achanak sabse zaroori cheez ban jayegi. Us waqt SAC theek wahi algorithm hoga. Isiliye wo roadmap (RQ3) me hai — hataya nahi gaya hai, sirf abhi uski baari nahi hai.

Reward design — jahan project ki asli mehnat hai

RL me algorithm chunna aasan hissa hai. Reward likhna mushkil hissa hai — kyunki agent bilkul wahi maximize karega jo aapne likha, wo nahi jo aapke dimaag me tha.

15.1 — Base metric: IoU

Intersection over Union
IoU = | D ∩ T | / | D ∪ T |
  • DDrawn — jitne pixels par ink lagi.
  • TTarget — jitne pixels par ink honi chahiye thi.
  • IoU1.0 = perfect. 0 = bilkul alag. Ye khud hi stray ink ko saza deta hai — kyunki galat jagah ki ink union badhati hai, intersection nahi. Isliye "poora kaagaz kaala kar do" wali cheating apne aap ruk jati hai.

15.2 — Reward = IoU ka badhna, IoU khud nahi

Agar reward har step par IoU hota, to agent ko sirf lambe episode ka faayda milta (ek achhi drawing 200 steps tak reward deti rehti). Isliye hum delta dete hain — is step me IoU kitna badha.

Hamara reward (rl/draw_env.py, _reward)
rt = wiou · ΔIoUt + wprox · (Φt − Φt−1) − ctime − wsmooth · mean|at − at−1|
  • ΔIoUMukhya signal. iou_weight=10.0. Ek khoobsurat ganitiya baat: ye poore episode me telescope karta hai — saare ΔIoU jodne par sirf final IoU bachta hai. Yaani "return maximize karna" = "achhi drawing banana", exactly.
  • Φ shapingPotential-based shaping. prox_weight=0.4. Pen ko target ke paas aane par hi reward, ink lagne se pehle. Isne "kuch mat banao" wale local optimum ko toda.
  • ctimePer-step laagat, abhi 0. Efficiency ke liye badhaya ja sakta hai.
  • smoothnesssmooth_penalty=0.02. Achanak dishaa badalne par chhoti saza → seedhi, saaf strokes.

15.3 — Potential-based shaping: ek guarantee ke saath

Reward me "madad" jodna khatarnaak hai — aksar agent madad ko hi hack kar leta hai. Lekin ek khaas roop me shaping ganitiya taur par surakshit hai (Ng, Harada & Russell, 1999): agar extra reward ek potential function ka farak ho, to optimal policy bilkul nahi badalti.

Potential-based shaping theorem
F(s, s′) = γΦ(s′) − Φ(s)  ⇒  optimal policy nahi badalti
  • FJodha gaya extra reward.
  • Φ(s)Koi bhi function jo state ki "achhaai" batata ho. Hamare yahan: Φ = −(pen se target ki nazdeeki doori) — pen target par ho to Φ = 0, door ho to negative.
  • guaranteeKyunki F poore episode me telescope hokar ek constant ban jata hai, wo kisi policy ko doosri se aage nahi kar sakta. Yaani hum seekhne ki raftaar badhate hain bina task ki paribhaasha badle.
rl/draw_env.pyshaping ka asli code
self._target_dt = cv2.distanceTransform(
    255 - self.target, cv2.DIST_L2, 3).astype(np.float32) / canvas_res
# har pixel se sabse nazdeek TARGET ink pixel ki doori, ek baar pehle hi nikaal li

def _potential(self):
    """Potential Phi = -(pen se sabse nazdeek target ink ki doori).
    Zyada achha = zyada bada (pen target par -> 0)."""
    col, row = self._world_to_px(*self.pen_xy)
    return -float(self._target_dt[row, col])

def _reward(self, iou):
    d_iou = iou - self._prev_iou          # mukhya signal
    self._prev_iou = iou
    r = self.iou_weight * d_iou

    phi = self._potential()               # shaping: bina task badle guidance
    r += self.prox_weight * (phi - self._prev_phi)
    self._prev_phi = phi

    r -= self.time_penalty
    return r
